Durable Execution runs long-lived workflows that can retry, sleep, wait for correlated events, and resume without losing completed step output.

Use it when a workflow needs to survive process restarts, external callbacks, human approval, or delayed work.

## Core concepts

| Concept | Description |
| --- | --- |
| Namespace | A durable execution boundary under the user or team API key owner, such as `billing`. |
| Function | SDK code that implements a durable workflow. |
| Workflow | A registered durable workflow version with a WebSocket worker runtime and one or more triggers. |
| Worker | Your process that connects to Final over WebSocket, leases work, and drains on shutdown. |
| Connect key | A namespace-scoped secret that lets a worker create a WebSocket session. |
| Event | A named payload that can schedule matching workflows or resume waiting runs. |
| Run | One execution of a workflow. Runs can be `queued`, `running`, `waiting`, `completed`, `failed`, or `cancelled`. |
| Signal | A payload sent to a waiting run, optionally targeting a specific step. |

The public API is mounted under:

```text
https://api.final.ai/v1/durable-execution/namespaces/{namespace}
```

For endpoint details, see the [Durable Execution API reference](/api-references/durable-execution).
