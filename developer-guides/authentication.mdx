---
title: "Authentication"
description: "Authenticate requests to the Final API with bearer credentials."
---

Final APIs use bearer authentication. Send your credential in the `Authorization` header:

```bash
Authorization: Bearer <credential>
```

Use the unified API host for public REST APIs:

```text
https://api.final.ai
```

## Choose a credential

| Credential | Use it for |
| --- | --- |
| Organization API key | Organization-scoped REST APIs, Virtual Machines team-owned creation with `teamId`, Agent Workspaces through an agent profile, Agent Disk team-owned disk creation with `teamId`, and API key management. |
| Team API key | Team-scoped Agent Workspaces, WebSocket Gateway, and Durable Execution requests. |
| User API key | User-scoped Agent Workspaces, WebSocket Gateway, Durable Execution, Secrets, private or team-owned Virtual Machines, and private or team-owned Agent Disk requests. |
| Production access token | Git repository management endpoints. |
| Minted Git credentials | Short-lived Git HTTPS clone, fetch, and push operations. |
| VM token | Scoped VM access where VM tokens are supported. VM tokens do not authenticate public API requests to `api.final.ai`. |

## Use API keys

Create API keys in Final under **Settings** > **API Keys**. Available scopes depend on your role and team membership.

Final API keys use the `final_sk` prefix. Production keys start with `final_sk_live_`; non-production keys start with `final_sk_test_`.

Store API keys in your secret manager and load them into your automation environment:

```bash
export FINAL_API_KEY="<api-key>"
```

Call public API endpoints with bearer auth:

```bash
curl "https://api.final.ai/v1/agent-workspaces" \
  -H "Authorization: Bearer ${FINAL_API_KEY}"
```

## Create API keys from the API

You can create organization API keys from automation with [create an API key](/api-references/api-keys/create).

The caller key must be organization-owned and must have the `api_keys:write` permission. A new key cannot request permissions that the caller key does not already have.

```bash
curl -X POST "https://api.final.ai/v1/api-keys" \
  -H "Authorization: Bearer ${FINAL_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "CI deploy",
    "permissions": ["apps:read"],
    "expiresAt": "2027-01-01T00:00:00.000Z"
  }'
```

The response includes the plaintext `value` once. Store it immediately.

## Use public IDs

Most public APIs return Final wire IDs for Final-minted resources. Use these IDs in API requests instead of raw UUIDs when an endpoint returns a prefixed ID.

Common prefixes include `org_` for organizations, `usr_` for users, `team_` for teams, `ak_` for API keys, `gsr_` for Git repositories, `dsk_` for Agent Disks, and `vm_` for Virtual Machines. VM subresources use prefixes such as `vmsh_` for shares, `vmcd_` for custom domains, `vmtk_` for VM tokens, and `vmsk_` for SSH keys.

Secrets are an exception. The Secrets API returns UUID secret IDs, and you can use either the UUID or the secret name in `secretId` path parameters.

## Authenticate Agent Workspaces

Agent Workspaces accepts organization-owned, team-owned, and user-owned API keys.

Organization-owned keys create workspaces through an agent profile. Include `agentProfileId` when you create a workspace or session.

Team-owned keys also require `agentProfileId`. The profile must belong to the same team as the API key, and list/get/update requests are scoped to that team's workspaces.

User-owned keys create workspaces as the key owner and do not require `agentProfileId`.

See [Agent Workspaces](/developer-guides/agent-workspaces) and the [Agent Workspaces API reference](/api-references/agent-workspaces).

## Authenticate WebSocket Gateway requests

Use a user-owned or team-owned API key to create short-lived WebSocket Gateway session tokens and to publish server-side channel or work queue events. Organization-owned API keys cannot mint or use gateway-scoped resources.

Gateway session tokens are scoped to the API key owner and expire quickly. Do not send your API key to browser or worker clients. Create a session token from your server, then pass the returned token and gateway URL to the client.

See [WebSocket Gateway](/developer-guides/websocket-gateway) and the [WebSocket Gateway API reference](/api-references/websocket-gateway).

## Authenticate Virtual Machines requests

Use a Final API key for Virtual Machines REST API requests.

User-owned API keys create private VMs when you omit `teamId`. To create a team-owned VM, pass `teamId` for a team the acting user belongs to.

Ownerless organization API keys can access organization VMs, but they must pass `teamId` when creating a VM. Every VM has exactly one owner scope: either `ownerUserId` for a private VM or `teamId` for a team-owned VM.

VM tokens are scoped VM credentials where supported. They do not authenticate public API requests to `api.final.ai`.

See [Virtual Machines](/developer-guides/virtual-machines) and the [Virtual Machines API reference](/api-references/virtual-machines).

## Authenticate Agent Disk requests

Use a Final API key for Agent Disk REST API requests.

User-owned API keys can create private disks by omitting `teamId`, or team-owned disks by passing a `teamId` for a team the user belongs to. Organization-owned API keys can access organization disks and must pass `teamId` when creating a disk because Agent Disk does not support organization-only disks.

Disk tokens, S3 credentials, and AWS STS users are disk-scoped access methods. They do not authenticate public API requests to `api.final.ai`.

See [Agent Disk](/developer-guides/agent-disk) and the [Agent Disk API reference](/api-references/agent-disk).

## Authenticate Durable Execution workers

Use a user-owned or team-owned API key for Durable Execution REST API requests, including sending events, triggering runs, and reading history. Durable Execution scopes work by organization, API key owner, and namespace.

Use a Durable Execution connect key for SDK workers. A connect key is scoped to one durable namespace and is exchanged for short-lived WebSocket worker session tokens by `connect()`. Store connect keys as server-side secrets and do not send them to browsers or untrusted clients.

See [TypeScript SDK and workers](/developer-guides/durable-execution/typescript-sdk).

## Authenticate Secrets requests

Use a user-owned API key for the Secrets API. Reads require `secrets:read`; creates, updates, value writes, and deletes require `secrets:write`.

Secrets are scoped to the API key owner inside the organization. Organization-owned API keys must resolve to a local user owner before they can access Secrets.

See [Secrets](/developer-guides/secrets) and the [Secrets API reference](/api-references/secrets/list).

## Authenticate Git operations

Git repository management endpoints currently use a production access token:

```bash
curl "https://api.final.ai/api/repositories" \
  -H "Authorization: Bearer ${access_token}"
```

For Git clone, fetch, and push, first mint short-lived Git credentials with [mint Git credentials](/api-references/repositories/mint-git-credentials). Use those credentials with the Git remote URL instead of sending your API key to Git.

## Handle auth errors

`401` means the credential is missing, malformed, expired, or invalid.

`403` means the credential is valid but cannot perform the requested action. Check the endpoint's required key owner type, permissions, and team membership. For API key creation through the public API, the caller key must be organization-owned, include `api_keys:write`, and already have every permission requested for the new key.
