---
title: "Authentication"
description: "Authenticate requests to the Final API with bearer credentials."
---

Final APIs use bearer authentication. Send your credential in the `Authorization` header:

```bash
Authorization: Bearer <credential>
```

Use the unified API host for public REST APIs:

```text
https://api.final.ai
```

## Choose a credential

| Credential | Use it for |
| --- | --- |
| Organization API key | Organization-scoped REST APIs, organization management, Computers team-owned creation with `teamId`, Agent Chats through an agent profile, Agent Disk team-owned disk creation with `teamId`, and API key management. |
| Team API key | Team-scoped REST APIs and team-owned delegated credential minting for WebSockets and Durable Execution workers. |
| User API key | User-scoped REST APIs and delegated credential minting for Git, WebSockets, and Durable Execution workers. |
| Delegated credential | Short-lived protocol credentials returned by the API, such as Git HTTPS credentials, WebSockets tokens, and Durable Execution worker credentials. |
| computer token | Scoped Computer access where computer tokens are supported. computer tokens do not authenticate public API requests to `api.final.ai`. |

## Use API keys

Create API keys in Final under **Settings** > **API Keys**. Available scopes depend on your role and team membership.

Final API keys use the `final_sk` prefix. Production keys start with `final_sk_live_`; non-production keys start with `final_sk_test_`.

Store API keys in your secret manager and load them into your automation environment:

```bash
export FINAL_API_KEY="<api-key>"
```

Call public API endpoints with bearer auth:

```bash
curl "https://api.final.ai/v1/agent-chats" \
  -H "Authorization: Bearer ${FINAL_API_KEY}"
```

API keys are the only customer credentials accepted as bearer tokens on the public REST API. Do not send Git credentials, WebSockets tokens, Durable worker tokens, computer tokens, or console session cookies to `api.final.ai`.

## Use delegated credentials

Delegated credentials are short-lived credentials minted from a Final API key. They use the `dc_` ID prefix and include `expiresAt`, `refreshAfter`, and `refreshBefore` lifecycle fields.

| Kind | Use it for |
| --- | --- |
| `git` | Git clone, fetch, and push against one repository. |
| `websockets` | WebSockets client sessions. |
| `durable_worker` | Durable Execution worker WebSocket sessions. |

Refresh a delegated credential only during its refresh window. Refresh and revoke requests must use the same API key that created the credential. See [Delegated credentials](/developer-guides/delegated-credentials) and the [Delegated credentials API reference](/api-references/delegated-credentials).

## Create API keys from the API

You can create organization API keys from automation with [create an API key](/api-references/api-keys/create).

The caller key must be organization-owned and must have the `api_keys:write` permission. A new key cannot request permissions, key kinds, or resource restrictions that exceed the caller key.

```bash
curl -X POST "https://api.final.ai/v1/api-keys" \
  -H "Authorization: Bearer ${FINAL_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Git automation",
    "permissions": ["repositories:read", "repositories:write"],
    "kind": "repository_automation",
    "resourceRestrictions": {
      "audiences": ["git"],
      "repositories": ["gsr_123"]
    },
    "expiresAt": "2027-01-01T00:00:00.000Z"
  }'
```

The response includes the plaintext `value` once. Store it immediately.

You can also [list organization API keys](/api-references/api-keys/list) and [revoke an organization API key](/api-references/api-keys/delete) with the same permission.

## Manage organizations

Organization management reads require `organizations:read`. Mutations require `organizations:write` and an organization-owned API key.

Use organization management APIs to read the current organization, list roles and members, manage invitations, and manage teams. See [Organization management](/developer-guides/organizations) and the [Organizations API reference](/api-references/organizations).

## API key kinds and restrictions

Use API key kinds and resource restrictions to limit what a key can mint.

| Kind | Intended delegated credentials |
| --- | --- |
| `general` | Any credential allowed by the key permissions and restrictions. |
| `repository_automation` | `git` credentials. |
| `websockets_issuer` | `websockets` credentials. |
| `durable_worker` | `durable_worker` credentials. |

| Restriction | Applies to | Example |
| --- | --- | --- |
| `audiences` | All delegated credentials | `["git"]`, `["websockets"]`, `["durable-execution"]` |
| `repositories` | Git credentials | `["gsr_123"]` |
| `namespaces` | Durable worker credentials | `["billing"]` |
| `websocketsResources` | WebSockets credentials | `["channel:chat", "work:customer-jobs"]` |

Use `*` inside a restriction list to allow every value for that restriction. An empty list denies every value.

## Use public IDs

Most public APIs return Final wire IDs for Final-minted resources. Use these IDs in API requests instead of raw UUIDs when an endpoint returns a prefixed ID.

Common prefixes include `org_` for organizations, `usr_` for users, `team_` for teams, `ak_` for API keys, `prof_` for agent profiles, `chat_` for agent chats, `sess_` for agent sessions, `fnod_` for Final Nodes, `gsr_` for Git repositories, `dsk_` for Agent Disks, and `comp_` for Computers. Computer subresources use prefixes such as `cshr_` for shares, `cdmn_` for custom domains, `ctok_` for computer tokens, and `cssh_` for SSH keys.

Secrets are an exception. The Secrets API returns UUID secret IDs, and you can use either the UUID or the secret name in `secretId` path parameters.

## Authenticate Agent Chats

Agent Chats accepts organization-owned, team-owned, and user-owned API keys.

Organization-owned keys create agent chats through an agent profile. Include `agentProfileId` when you create an agent chat or session.

Team-owned keys also require `agentProfileId`. The profile must belong to the same team as the API key, and list/get/update requests are scoped to that team's agent chats.

User-owned keys create agent chats as the key owner and do not require `agentProfileId`.

See [Agent Chats](/developer-guides/agent-chats) and the [Agent Chats API reference](/api-references/agent-chats).

## Authenticate WebSockets requests

Use a user-owned or team-owned API key to create short-lived WebSockets session tokens and to publish server-side channel or work queue events. Organization-owned API keys cannot mint or use WebSockets-scoped resources.

WebSockets session tokens are scoped to the API key owner and expire quickly. API-key-backed session creation uses the delegated credential lifecycle internally. Do not send your API key to browser or worker clients. Create a session token from your server, then pass the returned token and WebSocket URL to the client.

See [WebSockets](/developer-guides/websockets) and the [WebSockets API reference](/api-references/websockets).

## Authenticate Computers requests

Use a Final API key for Computers REST API requests.

User-owned API keys create private Computers when you omit `teamId`. To create a team-owned Computer, pass `teamId` for a team the acting user belongs to.

Ownerless organization API keys can access organization Computers, but they must pass `teamId` when creating a Computer. Every Computer has exactly one owner scope: either `ownerUserId` for a private Computer or `teamId` for a team-owned Computer.

computer tokens are scoped Computer credentials where supported. They do not authenticate public API requests to `api.final.ai`.

See [Computers](/developer-guides/computers) and the [Computers API reference](/api-references/computers).

## Authenticate Agent Disk requests

Use a Final API key for Agent Disk REST API requests.

User-owned API keys can create private disks by omitting `teamId`, or team-owned disks by passing a `teamId` for a team the user belongs to. Organization-owned API keys can access organization disks and must pass `teamId` when creating a disk because Agent Disk does not support organization-only disks.

Disk tokens, S3 credentials, and AWS STS users are disk-scoped access methods. They do not authenticate public API requests to `api.final.ai`.

See [Agent Disk](/developer-guides/agent-disk) and the [Agent Disk API reference](/api-references/agent-disk).

## Authenticate Durable Execution workers

Use a user-owned or team-owned API key for Durable Execution REST API requests, including sending events, triggering runs, and reading history. Durable Execution scopes work by organization, API key owner, and namespace.

Use a user-owned or team-owned API key for SDK workers. `connect()` uses that API key only to call the REST API, then mints and refreshes short-lived `durable_worker` delegated credentials for the worker WebSocket connection. Store the API key as a server-side secret and do not send it to browsers or untrusted clients.

See [TypeScript SDK and workers](/developer-guides/durable-execution/typescript-sdk).

## Authenticate Secrets requests

Use a user-owned API key for the Secrets API. Reads require `secrets:read`; creates, updates, value writes, and deletes require `secrets:write`.

Secrets are scoped to the API key owner inside the organization. Organization-owned API keys must resolve to a local user owner before they can access Secrets.

See [Secrets](/developer-guides/secrets) and the [Secrets API reference](/api-references/secrets/list).

## Authenticate Git operations

Use a user-owned API key for Git repository management endpoints. Reads require `repositories:read`. Creates, archives, deletes, and write-capable Git credential minting require `repositories:write`.

```bash
curl "https://api.final.ai/v1/repositories" \
  -H "Authorization: Bearer ${FINAL_API_KEY}"
```

For Git clone, fetch, and push, first mint short-lived Git credentials with [mint Git credentials](/api-references/repositories/mint-git-credentials). Use those credentials with the Git remote URL instead of sending your API key to Git.

For new automation, prefer [creating a `git` delegated credential](/api-references/delegated-credentials/create). It returns the same Git `username` and `password` inside the shared delegated credential lifecycle.

## Handle auth errors

`401` means the credential is missing, malformed, expired, or invalid.

`403` means the credential is valid but cannot perform the requested action. Check the endpoint's required key owner type, permissions, key kind, resource restrictions, and team membership. For API key creation through the public API, the caller key must be organization-owned, include `api_keys:write`, and already allow every permission and restriction requested for the new key.
