Final Cloud deploys app workloads from one manifest. Use it when you want a CI runner or agent to ship a service, scheduled job, one-off job, or Cloud Function without wiring together separate build, rollout, secret, and health-check systems.

A Final Cloud app has a stable app ID and owner scope. Each deployment submits a `final-cloud.yaml` manifest and optional source archive. Final stores the manifest, resolves artifacts and environment, rolls the declared workloads, and marks the deployment `healthy`, `failed`, or `rolled_back`.

## What you can deploy

| Workload | Use it for |
| --- | --- |
| Services | HTTP services backed by images or source builds. |
| Jobs | Scheduled and manually triggered work. |
| Cloud Functions | JavaScript HTTP handlers on Final-managed workerd runtime. |

## Deployment model

1. Create or reuse a Final Cloud app.
2. Submit a manifest through `/v1/final-cloud/deployments`.
3. Include a source archive when Final should build from source.
4. Poll app status or read deployment events.

The same app can be deployed many times. Each deploy records the manifest and creates a deployment result. If a runtime rollout fails after a previous healthy deployment exists, Final attempts to restore the previous healthy runtime state.

## Minimal manifest

```yaml
name: api

build:
  method: dockerfile
  context: .
  dockerfile: Dockerfile

services:
  - name: web
    port: 3000
    health:
      path: /health
    scaling:
      min: 1
      max: 2
```

## Authentication

Use a Final API key with `apps:read` to read app status and events. Use `apps:write` to create apps, submit deployments, and trigger jobs.

Deployment and job-run requests require a user-owned or team-owned API key so Final can attribute runtime actions and resolve scoped secrets.
