---
title: "Session tokens and grants"
description: "Mint short-lived WebSocket Gateway tokens with scoped grants for clients and workers."
---

WebSocket Gateway clients do not use Final API keys. Your server mints a short-lived session token with the exact grants a client needs, then the client authenticates over WebSocket with that token.

## Token flow

1. Your server authenticates to `api.final.ai` with a user-owned or team-owned API key.
2. Your server creates a gateway session token with narrow grants.
3. The client connects to the returned WebSocket URL.
4. The client sends an `auth` frame with the token.
5. The client performs only the operations allowed by its grants.

## Create a session token

```bash
curl -X POST "https://api.final.ai/v1/websocket-gateway/sessions" \
  -H "Authorization: Bearer ${FINAL_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{
    "clientId": "browser_1",
    "ttlMs": 600000,
    "grants": {
      "channels": [
        {
          "name": "workspace:wksp_123",
          "access": ["subscribe"]
        }
      ]
    },
    "metadata": {
      "app": "customer-portal"
    }
  }'
```

See [create a WebSocket Gateway session](/api-references/websocket-gateway/sessions/create).

## Grant types

| Grant | Access values |
| --- | --- |
| `channels` | `subscribe`, `publish`, `history`, `presence` |
| `rpc` | `send`, `receive` |
| `bridges` | `join`, `send`, `receive` |
| `workQueues` | `lease`, `heartbeat`, `complete`, `fail` |

Use `limits` on a grant to restrict `maxFrameBytes`, `maxFramesPerMinute`, or `maxSubscriptions`.

## Design guidance

Mint tokens for one client purpose at a time. A browser that only reads progress needs `subscribe`, not `publish`. A worker that processes jobs needs work queue access, not channel access.

Keep TTLs short. When a client needs to reconnect after expiry, have it request a new token from your server.
