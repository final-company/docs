Use merge queues to protect target branches and land reviewed pull requests in the order Final Git has validated them. A queue creates a candidate commit for the exact pull request set that would land on the branch.

<Warning>
  CI must report checks against the merge queue candidate SHA. Do not report required queue checks only on the pull request branch SHA.
</Warning>

For endpoint details, see the [merge queues API reference](/api-references/merge-queues/list).

## When to use a merge queue

Use a merge queue when `main`, `trunk`, or a release branch must stay green while many pull requests are landing. The queue tests the same candidate SHA that would become the target branch head, so passing checks on a stale pull request branch does not accidentally protect the wrong code.

You probably want a queue when:

- The target branch breaks after individually approved pull requests merge.
- Pull requests are rebased often because the branch changes underneath them.
- CI takes long enough that multiple approved changes are usually waiting.
- Stacked pull requests should land as a validated range instead of as unrelated single PRs.
- You need an audit trail for queue entries, attempts, candidate SHAs, and check results.

## How Final queues work

1. A pull request or stack range is enqueued for a target branch.
2. Final Git creates a merge candidate ref for the exact work that may land.
3. Your CI runs against the candidate SHA.
4. CI reports required statuses or check runs back to Final.
5. Final Git lands the candidate only after the required checks pass.
6. If checks fail, time out, or the pull request changes, the attempt fails or becomes invalid.

For stacked PRs, the queue entry can include the selected range of pull requests. This lets Final validate the code that will land together instead of treating each dependent pull request as if it were independent.

## Create or update a queue

Open the repository in Final and select **Git**. Configured queues appear under **Merge queues**.

A queue must exist for the target branch before users can enqueue pull requests. You can create or update the queue with the [create or update a merge queue endpoint](/api-references/merge-queues/create-or-update).

| Setting | Description |
| --- | --- |
| Target branch | The branch protected by the queue, such as `main`. |
| Required contexts | Commit status or check run names that must pass on the candidate SHA. |
| Required approvals | The number of approvals each pull request needs before it can land. |
| Strategy | How Final Git lands the candidate, such as `rebase` or `squash`. |
| Timeout | How long an attempt can wait for checks before it fails. |
| Enforced | Requires pull requests to land through the queue. |
| Paused | Stops the queue from starting new attempts. |

You can also enable speculative processing and batching:

| Setting | Description |
| --- | --- |
| Speculative processing | Lets Final Git prepare more than one candidate at a time. |
| Speculative concurrency | Limits how many speculative candidates can run. |
| Batching | Lets Final Git test multiple queue entries together. |
| Batch max size | Limits how many entries can be tested in one batch. |
| Batch isolation strategy | Controls how Final Git isolates a failing batch. |

See [create or update a merge queue](/api-references/merge-queues/create-or-update) for request and response fields.

## Enqueue pull requests

Click **Enqueue** on a pull request after it is ready for the target branch queue.

For stacked PRs, Final Git queues the selected range of the stack. The queue entry records every pull request included in that range, then creates one candidate commit for that set.

Queue entries can be reordered, fast-tracked, or removed before they land.

Use the [enqueue a pull request endpoint](/api-references/merge-queues/enqueue) to queue pull requests from automation.

Use `stackMergeabilityBypass: true` only for emergency partial-stack landings. It requires admin access.

## Queue stacks

When a stack is ready, enqueue the top pull request to queue the full stack range. Final Git includes the open pull requests from the stack root through the selected pull request.

For a lower-only landing, enqueue a pull request in the middle of the stack. Final Git includes the root through that selected pull request. Use this when foundational changes are ready but higher pull requests still need work.

Avoid partial-stack bypasses during normal development. They can land code while dependent open pull requests still expect a different stack shape.

## Run CI on a merge group

When a queue starts an attempt, Final Git creates a candidate ref with this format:

```text
refs/final/mq/{queueId}/attempts/{attemptId}/candidate
```

The attempt stores the candidate ref, candidate SHA, base SHA, selected pull requests, and required contexts. Treat the attempt as the source of truth for CI.

If you configure a webhook URL, Final Git sends a `merge_group` webhook when a candidate is ready:

```json
{
  "event": "merge_group",
  "queue_id": "mq_123",
  "entry_id": "mqe_123",
  "attempt_id": "mqa_123",
  "repo_id": "repo_123",
  "target_branch": "main",
  "candidate_ref": "refs/final/mq/mq_123/attempts/mqa_123/candidate",
  "candidate_sha": "abc123",
  "base_sha": "def456",
  "selected_pull_request_ids": ["pr_123"],
  "batch_entry_ids": ["mqe_123"],
  "required_contexts": ["ci/test"],
  "strategy": "rebase",
  "actor": "merge-queue-worker"
}
```

Webhook requests include these headers:

| Header | Description |
| --- | --- |
| `x-final-event` | The event name. For merge queues, this is `merge_group`. |
| `x-final-delivery` | The attempt ID for the delivery. |
| `x-final-signature-sha256` | An HMAC-SHA256 signature when a webhook secret is configured. |

The signature is computed from the raw request body and the queue webhook secret.

## Report required checks

Your CI job should fetch the candidate ref, test the candidate SHA, and report every required context for that SHA.

<Steps>
  <Step title="Receive the merge group webhook">
    Read `candidate_ref`, `candidate_sha`, `attempt_id`, and `required_contexts`.
  </Step>
  <Step title="Fetch the candidate">
    Fetch `candidate_ref` from the repository and check out `candidate_sha`.
  </Step>
  <Step title="Run the required jobs">
    Run the jobs named in `required_contexts`.
  </Step>
  <Step title="Report the result">
    Report each required context as `success`, `failure`, or `error` for `candidate_sha`.
  </Step>
</Steps>

Final Git lands the queue entry only after every required context passes on the candidate SHA. If a required context fails, the attempt fails and the queue entry does not land.

Report results with the [create a commit status endpoint](/api-references/checks/create-commit-status) or the [create a check run endpoint](/api-references/checks/create-check-run).

## CI integration checklist

| Check | Why it matters |
| --- | --- |
| Fetch `candidate_ref` | The candidate ref is the code Final may land. |
| Test `candidate_sha` | Required checks must attach to the candidate SHA, not the source branch head. |
| Report every required context | Missing contexts keep the attempt waiting until it times out. |
| Preserve `attempt_id` in logs | It lets you connect CI failures to queue activity. |
| Verify webhook signatures | The queue webhook can include `x-final-signature-sha256` when a secret is configured. |

## Candidate lifecycle

Queue attempts move through these states:

| State | Meaning |
| --- | --- |
| Created | Final Git has reserved the attempt. |
| Waiting for checks | The candidate ref exists and Final Git is waiting for CI. |
| Merged | The candidate landed on the target branch. |
| Failed | A required check failed or the attempt timed out. |
| Invalidated | The candidate no longer matches the pull request, stack, or queue state. |

Final Git may remove candidate refs after attempts finish. If a candidate ref disappears before an active attempt reaches a terminal state, Final Git restores it from the stored attempt record.

## Operating guidance

Start with a small required context list. Add more required checks after the queue has been running cleanly and your CI can report results reliably.

Use batching when several independent pull requests can be tested together. Use speculative processing when CI capacity can handle multiple candidates and you want the queue to prepare likely future states.

Pause the queue during CI outages or branch incidents. Existing entries remain visible, but Final Git stops starting new attempts until you resume it.
