Use Final Git pull requests to review changes before they land on a target branch. A pull request tracks the source branch, target branch, head commit, review state, checks, and stack position.

Open the repository in Final and select the **Git** tab to see pull requests and merge queues.

For endpoint details, see the [pull requests API reference](/api-references/pull-requests/list).

## What you can do

| Goal | Use |
| --- | --- |
| Review one branch | Create a pull request from a source branch to a target branch. |
| Split a large change | Create [stacked PRs](/developer-guides/git/stacked-prs), each depending on the previous one. |
| Keep work moving during review | Continue building upstack while reviewers look at the lower pull requests. |
| Land reviewed work safely | Use **Merge when ready** or enqueue the pull request through a merge queue. |
| Repair changed branch history | Use stack repair, split, detach, or reorder controls when dependencies change. |

## Pull request lifecycle

1. Push a source branch to the repository.
2. Create a pull request against the target branch.
3. Mark it as **Draft** while the change is still moving, or **Ready** when reviewers should act.
4. Review the diff, comments, checks, and stack position.
5. Update the branch or stack in response to feedback.
6. Use **Merge when ready** or enqueue the pull request after it satisfies review and check requirements.

## Create a pull request

Before you create a pull request, push your source branch to the repository.

<Steps>
  <Step title="Open the Git tab">
    Open the repository in Final and select **Git**.
  </Step>
  <Step title="Enter the pull request details">
    Enter a title, source branch, and target branch.
  </Step>
  <Step title="Choose draft or ready">
    Use **Draft** while the branch is still changing. Use **Ready** when the pull request is ready for review.
  </Step>
  <Step title="Create the pull request">
    Click **Create PR**.
  </Step>
</Steps>

Use the [create a pull request endpoint](/api-references/pull-requests/create) to create pull requests from automation.

## Review changes

Each pull request shows commits, changed files, review state, checks, and recent activity. Click **Show diff** to inspect the patch.

You can leave one of three review states:

| Action | Use it when |
| --- | --- |
| **Approve** | The pull request is ready to merge. |
| **Comment** | You want to leave feedback without blocking the pull request. |
| **Request changes** | The author needs to update the pull request before it merges. |

Use the API to [list pull requests](/api-references/pull-requests/list), [read pull request details](/api-references/pull-requests/get), [fetch a diff](/api-references/pull-requests/get-diff), or [create a review](/api-references/pull-requests/create-review).

## Use merge when ready

Click **Merge when ready** when a pull request should enter the merge queue after it satisfies the queue requirements.

If the target branch has an enforced merge queue, Final Git lands the pull request through the queue. It does not merge directly into the protected branch.

Use the [update a pull request endpoint](/api-references/pull-requests/update) to set `mergeWhenReady` from automation.

## Work with stacked PRs

A stacked PR is a pull request that depends on another pull request in the same repository and target branch. Use stacks when a large change is easier to review as smaller pull requests.

Final Git validates the stack before it saves it. The parent pull request must be an ancestor of the child pull request.

Stacks work best when each pull request is understandable on its own. The lower pull requests should establish foundations, and the higher pull requests should build on them. Reviewers can then approve early pieces while later pieces are still changing.

<Steps>
  <Step title="Create the base pull request">
    Create the first pull request against the target branch.
  </Step>
  <Step title="Create a child branch">
    Branch from the base pull request branch, make your next change, and push the child branch.
  </Step>
  <Step title="Create the child pull request">
    Create another pull request against the same target branch.
  </Step>
  <Step title="Set the parent">
    Use the **Parent** menu to select the pull request that the child depends on.
  </Step>
</Steps>

To create a stacked pull request with the API, pass `parentPullRequestId` to the [create a pull request endpoint](/api-references/pull-requests/create).

For a deeper guide, see [stacked PRs](/developer-guides/git/stacked-prs).

## Review stacked PRs

Start with the pull request closest to the target branch. That is the root of the stack. Review upward from there when you are assigned to multiple pull requests in the same stack.

Treat each pull request as an independent review unit. If a pull request only makes sense after reading the entire stack, split it differently or move code between pull requests before review.

Use **Draft** for pull requests that are still being reshaped. Use **Ready** when the pull request is ready for reviewer action, even if higher pull requests in the stack are still in progress.

## Update a stack

Use stack controls when the dependency chain changes:

| Control | What it does |
| --- | --- |
| **Parent** | Sets or clears the pull request that this pull request depends on. |
| **Repair stack** | Refreshes stack metadata after branch heads change. |
| **Split** | Detaches this pull request and the pull requests above it from the lower stack. |
| **Move earlier** | Moves a pull request closer to the stack root. |
| **Move later** | Moves a pull request farther from the stack root. |

If a stack change affects queued work, Final Git removes the affected queue entries. Enqueue the updated stack again after the stack is valid.

Use these API endpoints to update stacks:

| Endpoint | Description |
| --- | --- |
| [Set pull request parent](/api-references/pull-requests/set-parent) | Sets or clears a parent pull request. |
| [Detach a pull request](/api-references/pull-requests/detach) | Detaches a pull request from its stack. |
| [Repair a pull request stack](/api-references/pull-requests/repair-stack) | Refreshes stack metadata. |
| [Split a pull request stack](/api-references/pull-requests/split-stack) | Splits a stack at a pull request. |
| [Reorder a pull request stack](/api-references/pull-requests/reorder-stack) | Reorders every pull request in a stack. |

## Queue a stack

Click **Enqueue** on the top pull request to queue the full stack. Final Git includes the open pull requests from the stack root through the selected pull request.

For a partial landing, click a **Through #** button to queue only the lower part of the stack through that pull request.

<Warning>
  Final Git blocks queue entries that omit open pull requests above the selected range. This prevents landing a middle pull request while its dependent pull requests remain open.
</Warning>

Use the [enqueue a pull request endpoint](/api-references/merge-queues/enqueue) to add a pull request or stack range to a merge queue.

## Stack design guidance

Keep stack roots small and stable. A volatile root forces more updates up the stack and makes review harder.

Split by review boundary, not by file count. Good stack slices include a schema change, a backend behavior change, a UI integration, or a cleanup that can be reviewed independently.

Queue the full stack when every open pull request in the range is ready. Queue a lower range when you want to land foundations first and keep higher work open.
