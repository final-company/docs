---
title: "Architecture"
description: "How Secrets handles security, durability, consistency, scalability, and latency."
---

Secrets stores sensitive values for agents, automation, and services. It separates metadata from encrypted values so callers can discover and manage secrets without exposing plaintext.

## Security

Secret values are encrypted before persistence and decrypted only for authorized value reads. List and metadata responses do not return plaintext values.

Access is scoped by organization and owner. Public API permissions split read and write operations with `secrets:read` and `secrets:write`, and value access still goes through the value-specific path.

## Scalability and durability

Secrets keeps stable identity separate from secret values. A secret can retain its ID, name, tags, and description while its encrypted value changes over time.

Value rotation advances encrypted value state without turning the secret into a new resource. That gives applications a stable reference while preserving rotation history and audit context.

## Consistency

A secret name resolves inside the caller's namespace. Metadata updates, value writes, and deletes are scoped to that namespace, so the same name in a different owner scope does not refer to the same secret.

Value reads require explicit access and return the current stored value for that secret. Metadata reads do not decrypt values, which keeps discovery separate from use.

## Latency

Metadata operations stay lightweight because they do not decrypt secret values. Callers can list and inspect secrets using metadata, then read the sensitive value only when a trusted runtime needs it.

Secrets should not be used as a general document store or agent memory. Keep it for sensitive configuration and pass references to the systems that need to resolve the value at execution time.
