Use Secrets to store values that automation needs without putting plaintext credentials in code, prompts, logs, or configuration files.

Secrets are scoped to the API key owner inside the organization. Reads require `secrets:read`; creates, updates, value writes, and deletes require `secrets:write`.

## What you can store

| Secret | Example use |
| --- | --- |
| Provider tokens | GitHub, Slack, Linear, cloud provider, or internal service tokens used by automation. |
| Deploy credentials | Keys or tokens needed by release jobs, preview builders, or deployment agents. |
| Agent integration settings | API tokens an agent can use through trusted tooling without showing the value in a prompt. |
| Webhook signing secrets | Shared secrets for validating inbound events. |
| Short-lived bootstrap values | Credentials your server rotates or replaces during setup flows. |

Do not use Secrets as a general database. Store the sensitive value in Secrets, and keep non-sensitive workflow state in your application.

## Core concepts

| Concept | Description |
| --- | --- |
| Secret metadata | The `id`, `name`, `description`, `tags`, `createdAt`, and `updatedAt` fields. |
| Secret value | The sensitive string stored for the secret. Values are returned only by the value read endpoint. |
| Name | A stable identifier you choose, such as `github_token` or `deploy.prod.token`. |
| Tags | String key-value metadata for ownership, service, environment, rotation, or source information. |
| Rotation | Replacing the current value while keeping the same secret name and metadata. |
