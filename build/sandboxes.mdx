With compute, the agent can run shell commands, read and write files, and run your tests, the way a developer would in a terminal. The agent requires compute by **capability**; the caller provides a **sandbox** for each capability: a computer placed by the [Sandbox Router](/sandbox-router/overview) on Final or another provider, a person's own machine running Final Device, or the caller's own process.

## Require compute

```ts agent.ts
import { defineAgent } from '@finalai/agents';

export const agent = defineAgent({
  name: 'Test Runner',
  description: 'Runs the test suite and explains failures.',
  instructions: 'Run the tests, read the failures, and explain the likely cause of each.',
  require: {
    harness: { permissionMode: 'ask' },
    compute: { files: 'write', shell: 'execute' },
  },
});
```

| Capability | Access | What the model does with it |
| --- | --- | --- |
| `files` | `read`, `write` | Reads and edits files with the harness's file tools. |
| `shell` | `execute` | Runs commands, manages the processes they start, and gets a URL for a port one listens on. |
| `computerUse` | `view`, `control` | Sees and operates a desktop. |
| `browserUse` | `view`, `control` | Sees and operates a browser. |

The agent never names a machine. The same agent works on any sandbox that serves those capabilities.

## Provide a sandbox

Create a sandbox in the project, then provide it for each capability. `files` and `shell` must be the same sandbox:

```ts run.ts
import { createClient } from '@finalai/agents/client';
import { finalCredits, serverlessPi } from '@finalai/agents/harnesses';
import { computer, defineSandboxSetup } from '@finalai/agents/sandboxes';
import { agent } from './agent.js';

const client = createClient({ auth: { apiKey: process.env.FINAL_API_KEY! } });
const project = client.project({ id: process.env.FINAL_PROJECT_ID! });

const sessionId = crypto.randomUUID();
const box = await project.sandboxes.create(computer({ image: 'docker.io/library/node:26-bookworm' }), {
  setup: defineSandboxSetup({
    repositories: [{ alias: 'web', url: 'https://github.com/acme/web.git', ref: 'main' }],
    steps: [{ cwd: 'web', run: 'npm ci' }],
  }),
  ownedBy: { session: sessionId },
});

const { response } = await project.sessions.create({
  id: sessionId,
  agent,
  provide: {
    harness: serverlessPi({ model: 'gpt-6.1-sol', inference: finalCredits() }),
    compute: { files: box, shell: box },
  },
  message: 'Run the tests and explain the first failure.',
});
console.log(await response!.text());
```

- **Creating a sandbox boots nothing.** The machine starts the first time the agent or your code uses it.
- **A [sandbox setup](/build/sandbox-setups)** says what should be on the machine: repositories, variables, setup steps, services, and named commands. It works on any provider.
- **`ownedBy`** ties the sandbox to a session, a conversation, or a [Task](#sandboxes-for-tasks), and it's deleted with its owner. Choosing the session's `id` up front lets you create the sandbox first. Without an owner, the sandbox lives until you call `box.delete()`.
- **`idempotencyKey`** makes a retried create return the sandbox the first call made.

Leave `compute` out and the model's files and shell run in the calling process, in its working directory. See [where code and compute run](/build/where-code-runs).

## Choose how long files last

A sandbox's disk lasts as long as the sandbox does, so you choose by what you provide:

| You want | Provide |
| --- | --- |
| A fresh machine per task | A new sandbox owned by the session. |
| One machine shared by every agent in a chat | A sandbox owned by the conversation, in the conversation's `provide`. |
| A long-lived machine for a team or a schedule | A sandbox with no owner, provided by id to every session that should use it. |
| One machine for a Task and its steps | A sandbox owned by the Task. See [sandboxes for Tasks](#sandboxes-for-tasks). |

A computer pauses when it has been idle for its `idleTimeoutSeconds`, keeping its disk and processes, and resumes on next use.

## Sandboxes for Tasks

A [Task](/tasks/overview)'s machines belong to the Task, not to the sessions working it. A session that fails and is replaced picks up the same machine, with its checkout and branches. A Task's sandboxes are deleted when it completes or is canceled; reopening a failed Task keeps them.

Each step's `workspace` says where it works:

| Workspace | Machine | Good for |
| --- | --- | --- |
| `shared` | The root's sandbox. Each step works in its own Git worktree and branch. Steps that share it must run the same agent, since a sandbox's outbound identity is its own. | Several agents coding on one machine, with integrate and review steps working on the local branches. |
| `fork` | A copy of the root's sandbox, made when the step starts, on a provider that can fork. | Best-of-N attempts and isolated experiments. |
| `own` | The step's own sandbox. | Heavy, untrusted, or conflicting work. |
| `none` | No machine: Final's Workers runtime. | Research, analysis, and writing; wide fan-out. |

`exclusiveKey` keeps steps that would fight over ports or services from running at once. A runner creates a Task's sandboxes with `ownedBy: { task: taskId }`, and copies one for a `fork` step with `project.sandboxes.fork(sandboxId, { task: stepId, idempotencyKey })`; the copy belongs to the step. `project.sandboxes.list({ task })` lists a Task's sandboxes.

Project viewers can read a Task's sandboxes, without waking them, through `project.tasks.sandboxes(taskId)`: `files`, `file`, `searchFiles`, `processes`, and `preview`. Their spend counts toward the Task's budget.

## Ask before commands run

The agent's `require.harness.permissionMode` is the most its harness may do unasked. The caller can hold it stricter with `permissionMode` in the [harness settings](/harnesses/settings):

| Mode | What happens |
| --- | --- |
| `ask` | The agent asks before running a command or changing a file. Reading is allowed. |
| `review` | Edits proceed. Commands and outside actions wait for a person. |
| `auto` | Commands and edits run without asking. |

When the agent asks, the turn pauses until a person answers in your app. See [handle approvals](/client/sessions#handle-approvals). For finer control, the agent's `toolPolicy` asks before one capability even when the mode allows it, like `toolPolicy: { 'files.write': 'ask' }`.

A common pattern is to keep `ask` for the built-in shell and give the agent a dedicated tool for the commands it runs often, like a [`run_tests` tool](/build/tools#use-the-agents-sandbox-from-a-tool) that calls `ctx.sandbox('shell')`.

## Use the sandbox from your own code

A sandbox handle runs commands and reads what's known about the machine, outside any session:

```ts
const result = await box.run({ command: 'git log -1 --oneline', cwd: 'web' });
console.log(result.exitCode, result.stdout);

const description = await box.description();
console.log(description.checkouts); // [{ alias: 'web', path: '/.../web', ... }]
```

`box.description()` lists real checkout paths, service URLs, named commands, and the setup's notes. The same description is a file in the sandbox, but Final doesn't put it in the agent's context; add what the agent should know to its message or the conversation's [standing context](/client/conversations#give-agents-standing-context).

## Run on a Final Device

To have the agent work on a person's own computer, create a sandbox from `device`. The machine needs [Final Device](/device/overview) installed and connected:

```ts
import { device } from '@finalai/agents/sandboxes';

const laptop = await project.sandboxes.create(device({ deviceId: '6f1c2a7e-3b4d-4e8f-9a21-7c5d0e1b2f34' }));
```

Pass `pairing` with a pairing code the owner approved instead of `deviceId`. A device takes no sandbox setup. If it's paused or offline, the agent can't reach it; Final never moves the work to another machine. Commands run as the machine's operating system account with all of its access, so keep the permission mode on `ask` until you trust the agent.

## Route across providers

Computers go through the [Sandbox Router](/sandbox-router/overview). By default they run on Final VMs. Add routing preferences to the computer's environment and the router places each sandbox on whichever provider meets them, such as E2B, Daytona, Modal, Vercel Sandbox, or Final, with Final's account or your own provider key:

```ts
const box = await project.sandboxes.create(
  {
    provider: 'computer',
    environment: { routing: { only: ['e2b', 'daytona'], sort: 'price', byok: 'first' } },
  },
  { setup },
);
```

`routing` takes the router's `only`, `order`, `ignore`, `sort`, `byok`, `maxPricePerHour`, and `require`; see [routing](/sandbox-router/routing) and [your own keys and billing](/sandbox-router/byok-and-billing). Naming `only` lifts the default pin to Final VMs. The same sandbox setup, the same agent, and the same tools work wherever a sandbox lands. In the dashboard, the project's **Sandboxes for agents** settings choose these preferences, your provider keys, and a monthly spend limit for the sandboxes Final starts for the project's agents.

What a placed sandbox offers depends on the provider it landed on, never on the registration alone. An agent never gets a tool its sandbox can't serve.

### Computer use on any provider

Computer use is a routing requirement, not a choice of provider. Set `computerUse: true` and the router places the sandbox only on a provider with a verified desktop, starting from its `desktop` image when you name none. The agent drives the desktop through the router's provider-neutral computer-use API, so the same agent works on an E2B, Daytona, or Final desktop, with the project's other routing preferences still applied.

<Note>
`@finalai/daytona-agent-provider` is deprecated. Route to Daytona with `routing: { only: ['daytona'], byok: 'only' }` and your Daytona key stored with the router instead.
</Note>

## Run your own provider

`project.sandboxes.providers()` lists the providers your project can create sandboxes on, each with the JSON Schema of its options. To add your own, write a sandbox provider: code that creates, attaches, parks, and deletes machines, and optionally forks them, written against the provider contract in `@finalai/agent-provider`. Serve it at a URL with `serveSandboxProvider` from `@finalai/agent-provider/sandbox/remote`, then register that URL in your project:

```ts
await project.sandboxProviders.register({
  name: 'acme-vms',
  url: 'https://sandboxes.example.com',
  forwardSecrets: ['ACME_VMS_TOKEN'],
});

const box = await project.sandboxes.create({ provider: 'acme-vms', environment: { size: 'large' } });
```

Final reads the provider's discovery document when you register it, and authenticates every call with a [platform identity assertion](/build/integrations#verify-calls-from-final), which `serveSandboxProvider` verifies. `forwardSecrets` names project secrets the provider receives, resolved in the sandbox's project. Registrations in a parent project are available to the projects below it. The [`@finalai/agent-provider` README](https://www.npmjs.com/package/@finalai/agent-provider) covers the contract, the wire, and the conformance kit that checks a provider; `@finalai/agent-provider/testing/mcp` has an in-process harness for testing a provider's MCP channels. A provider that implements `fork` reports the `fork` feature in its discovery document; [`fork` workspaces](#sandboxes-for-tasks) need one.

## Computer options

`computer()` holds only what Final's computers control. What goes on the machine is the [sandbox setup](/build/sandbox-setups).

<ParamField path="image" type="string">
  An OCI image reference such as `docker.io/library/node:26-bookworm`, a registered router image (`simg_...`), or `desktop` for the router's desktop image. Defaults to Final's sandbox image.
</ParamField>

<ParamField path="build" type="{ steps, verify }">
  Commands baked into a base image once, before any sandbox uses it, such as installing toolchains. `verify` commands fail the build if they fail. Each step takes `run` and `timeoutMinutes` (default 20).
</ParamField>

<ParamField path="machine" type="{ vcpu?, memoryMb?, diskGb? }">
  The machine's size. `vcpu`, from 1 to 32, is the most CPU it can burst to; it's guaranteed 0.25 vCPU and uses more when the host has idle CPU. `memoryMb` is fixed, fully reserved memory; it defaults to 4096. `diskGb` defaults to 12. See [CPU and memory](/vm-platform/cpu-and-memory).
</ParamField>

<ParamField path="region" type="string">
  Where the computer runs.
</ParamField>

<ParamField path="idleTimeoutSeconds" type="number">
  Idle time before the computer pauses, keeping its disk and processes. Between 60 seconds and 7 days.
</ParamField>

<ParamField path="routing" type="{ only?, order?, ignore?, sort?, byok?, maxPricePerHour?, require? }">
  Where the router may place the computer. See [route across providers](#route-across-providers).
</ParamField>

<ParamField path="computerUse" type="boolean">
  Place the computer only on a provider with a verified desktop, for an agent that requires `computerUse`. See [computer use on any provider](#computer-use-on-any-provider).
</ParamField>

To create, snapshot, or manage VMs directly from your own code, see [Final VMs](/vm-platform/overview).
