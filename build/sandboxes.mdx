With compute, the agent can run shell commands, read and write files, and run your tests, the way a developer would in a terminal. The agent requires compute by **capability**; the caller provides a **sandbox** for each capability: a Final computer, a person's own machine running Final Device, a Daytona sandbox, or the caller's own process.

## Require compute

```ts agent.ts
import { defineAgent } from '@finalai/agents';

export const agent = defineAgent({
  name: 'Test Runner',
  description: 'Runs the test suite and explains failures.',
  instructions: 'Run the tests, read the failures, and explain the likely cause of each.',
  require: {
    harness: { permissionMode: 'ask' },
    compute: { files: 'write', shell: 'execute' },
  },
});
```

| Capability | Access | What the model does with it |
| --- | --- | --- |
| `files` | `read`, `write` | Reads and edits files with the harness's file tools. |
| `shell` | `execute` | Runs commands, manages the processes they start, and gets a URL for a port one listens on. |
| `computerUse` | `view`, `control` | Sees and operates a desktop. |
| `browserUse` | `view`, `control` | Sees and operates a browser. |

The agent never names a machine. The same agent works on any sandbox that serves those capabilities.

## Provide a sandbox

Create a sandbox in the project, then provide it for each capability. `files` and `shell` must be the same sandbox:

```ts run.ts
import { createClient } from '@finalai/agents/client';
import { finalCredits, serverlessPi } from '@finalai/agents/harnesses';
import { computer, defineSandboxSetup } from '@finalai/agents/sandboxes';
import { agent } from './agent.js';

const client = createClient({ auth: { apiKey: process.env.FINAL_API_KEY! } });
const project = client.project({ id: process.env.FINAL_PROJECT_ID! });

const sessionId = crypto.randomUUID();
const box = await project.sandboxes.create(computer({ image: 'docker.io/library/node:26-bookworm' }), {
  setup: defineSandboxSetup({
    repositories: [{ alias: 'web', repository: 'acme/web', ref: 'main' }],
    steps: [{ cwd: 'web', run: 'npm ci' }],
  }),
  ownedBy: { session: sessionId },
});

const { response } = await project.sessions.create({
  id: sessionId,
  agent,
  provide: {
    harness: serverlessPi({ model: 'gpt-6.1-sol', inference: finalCredits() }),
    compute: { files: box, shell: box },
  },
  message: 'Run the tests and explain the first failure.',
});
console.log(await response!.text());
```

- **Creating a sandbox boots nothing.** The machine starts the first time the agent or your code uses it.
- **A [sandbox setup](/build/sandbox-setups)** says what should be on the machine: repositories, variables, setup steps, services, and named commands. It works on any provider.
- **`ownedBy`** ties the sandbox to a session or conversation, and it's deleted with its owner. Choosing the session's `id` up front lets you create the sandbox first. Without an owner, the sandbox lives until you call `box.delete()`.
- **`idempotencyKey`** makes a retried create return the sandbox the first call made.

Leave `compute` out and the model's files and shell run in the calling process, in its working directory. See [where code and compute run](/build/where-code-runs).

## Choose how long files last

A sandbox's disk lasts as long as the sandbox does, so you choose by what you provide:

| You want | Provide |
| --- | --- |
| A fresh machine per task | A new sandbox owned by the session. |
| One machine shared by every agent in a chat | A sandbox owned by the conversation, in the conversation's `provide`. |
| A long-lived machine for a team or a schedule | A sandbox with no owner, provided by id to every session that should use it. |

A computer pauses when it has been idle for its `idleTimeoutSeconds`, keeping its disk and processes, and resumes on next use.

## Ask before commands run

The agent's `require.harness.permissionMode` is the most its harness may do unasked. The caller can hold it stricter with `permissionMode` in the [harness settings](/harnesses/settings):

| Mode | What happens |
| --- | --- |
| `ask` | The agent asks before running a command or changing a file. Reading is allowed. |
| `review` | Edits proceed. Commands and outside actions wait for a person. |
| `auto` | Commands and edits run without asking. |

When the agent asks, the turn pauses until a person answers in your app. See [handle approvals](/client/sessions#handle-approvals). For finer control, the agent's `toolPolicy` asks before one capability even when the mode allows it, like `toolPolicy: { 'files.write': 'ask' }`.

A common pattern is to keep `ask` for the built-in shell and give the agent a dedicated tool for the commands it runs often, like a [`run_tests` tool](/build/tools#use-the-agents-sandbox-from-a-tool) that calls `ctx.sandbox('shell')`.

## Use the sandbox from your own code

A sandbox handle runs commands and reads what's known about the machine, outside any session:

```ts
const result = await box.run({ command: 'git log -1 --oneline', cwd: 'web' });
console.log(result.exitCode, result.stdout);

const description = await box.description();
console.log(description.checkouts); // [{ alias: 'web', path: '/.../web', ... }]
```

`box.description()` lists real checkout paths, service URLs, named commands, and the setup's notes. The same description is a file in the sandbox, but Final doesn't put it in the agent's context; add what the agent should know to its message or the chat's instructions.

## Run on a Final Device

To have the agent work on a person's own computer, create a sandbox from `device`. The machine needs [Final Device](/device/overview) installed and connected:

```ts
import { device } from '@finalai/agents/sandboxes';

const laptop = await project.sandboxes.create(device({ deviceId: '6f1c2a7e-3b4d-4e8f-9a21-7c5d0e1b2f34' }));
```

Pass `pairing` with a pairing code the owner approved instead of `deviceId`. A device takes no sandbox setup. If it's paused or offline, the agent can't reach it; Final never moves the work to another machine. Commands run as the machine's operating system account with all of its access, so keep the permission mode on `ask` until you trust the agent.

## Use another provider

Any sandbox provider works the same way. Daytona sandboxes run in your own Daytona account:

```ts
import { daytona } from '@finalai/daytona-agent-provider/sandboxes';

const box = await project.sandboxes.create(
  daytona({ credential: { secretRef: 'DAYTONA_API_KEY' }, image: 'node:26' }),
  { setup },
);
```

`project.sandboxes.providers()` lists the providers your project can create sandboxes on, each with the JSON Schema of its options.

## Computer options

`computer()` holds only what Final's computers control. What goes on the machine is the [sandbox setup](/build/sandbox-setups).

<ParamField path="image" type="string">
  An OCI image reference such as `docker.io/library/node:26-bookworm`. Defaults to Final's sandbox image.
</ParamField>

<ParamField path="build" type="{ steps, verify }">
  Commands baked into a base image once, before any sandbox uses it, such as installing toolchains. `verify` commands fail the build if they fail. Each step takes `run` and `timeoutMinutes` (default 20).
</ParamField>

<ParamField path="machine" type="{ vcpu?, memoryMb?, diskGb? }">
  The machine's size.
</ParamField>

<ParamField path="region" type="string">
  Where the computer runs.
</ParamField>

<ParamField path="idleTimeoutSeconds" type="number">
  Idle time before the computer pauses, keeping its disk and processes. Between 60 seconds and 7 days.
</ParamField>

To create, snapshot, or manage VMs directly from your own code, see [Final VMs](/vm-platform/overview).
