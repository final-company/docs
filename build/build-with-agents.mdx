There's no special builder agent: any agent with Final's tools can create and edit agents. That includes your project's agent in Final and, through the [MCP gateway](/mcp-gateway/overview), Claude Code, Codex or Cursor. The same agents build [workflows](/workflows/build-with-agents).

## Ask your project's agent

In a chat, ask your project's agent for the agent you want, or name an existing agent and say what to change:

> Make an agent for our support channel that answers billing questions from our help center and hands refunds to a person.

The agent writes the agent's source, checks it, tries it, and asks you before it creates, tries or publishes anything.

## Use your own coding agent

Connect Claude Code, Codex or Cursor to the [MCP gateway](/mcp-gateway/quickstart), then ask it to work on an agent. It finds Final's agent tools through the gateway's tool search.

> Copy the triage agent in my Acme project, make it label issues by component instead of by team, and publish it as triage-by-component.

## The agent tools

| Tool | What it does |
| --- | --- |
| `create_agent` | Creates an agent in the project, blank or as a copy of a published agent. Needs your approval. |
| `read_agent_source` | Lists the files of the agent's newest draft and its revision. |
| `read_agent_file` | Reads one file of a draft. |
| `edit_agent_file` | Changes one file by exact text replacements against one revision. |
| `write_agent_file` | Writes one file whole, new or replacing the one at its path. |
| `delete_agent_file` | Removes one file. |
| `run_agent_shell` | Runs a bash command over the draft's files, such as `grep`, `sed` or `mv`. Files it changes become the next draft. |
| `check_agent` | Makes the agent's document from the draft and type-checks it, and returns the diagnostics with their files and lines. |
| `test_agent` | Tries a draft before publishing: starts one test session of it with a first message. Needs your approval. |
| `read_agent_test` | Reads a test session's state, the draft's latest reply, and any question waiting for you. |
| `publish_agent` | Publishes a draft revision as the agent's next version. Needs your approval. |
| `update_agent_from_upstream` | Merges the newest published version of the agent this one was copied from into a new draft. |

Changes are checked against the revision they were made from, so an agent never overwrites a change it hasn't read. Creating, trying and publishing need editor access to the project.

An agent in Final doesn't carry these tools' definitions on every turn. It finds them as the `final.agents` group in its tool search, next to `final.workflows` for [workflows](/workflows/build-with-agents), and reads their definitions when building comes up.

`run_agent_shell` interprets bash and its usual commands over the draft's files alone: there's no network, no Node.js or npm, and no other files. Use it to search and reorganize files, and `check_agent` to check the agent.

## Source files

An agent created or edited on Final is a set of files, laid out as in [your own repository](/build/project-structure): an entry module, `agent.ts`, that exports the agent, any modules it imports, and the text files it reads, such as its instructions and skills.

<CodeGroup>

```ts agent.ts
import { defineAgent, markdown, skill } from '@finalai/agents';
import { releaseStatus } from './tools/release-status.ts';

export const agent = defineAgent({
  name: 'Release Assistant',
  instructions: markdown('./instructions.md', { from: import.meta.url }),
  skills: [skill('./skills/release-checklist', { from: import.meta.url })],
  tools: { release_status: releaseStatus },
  require: { harness: { permissionMode: 'ask' } },
});
```

```ts tools/release-status.ts
import { defineServerlessTool } from '@finalai/agents';
import * as z from 'zod';

export const releaseStatus = defineServerlessTool({
  description: 'Get the CI and sign-off status of a release.',
  inputSchema: z.object({ version: z.string() }),
  execute: async ({ version }) => {
    const response = await fetch(`https://releases.acme.com/api/releases/${version}`);
    return await response.json();
  },
});
```

```md instructions.md
You help maintainers decide whether a release is ready to ship.
Call release_status before you assess a release, and end with the next action.
```

</CodeGroup>

Modules import each other by relative path (`./tools/release-status.ts`, or `./tools/release-status.js` for the TypeScript file it compiles from) and otherwise import only `@finalai/agents` (and its authoring entry points such as `@finalai/agents/harnesses`) and `zod`. Tools and hooks are [serverless](/build/tools#in-process-or-serverless). That's because Final makes the agent's [document](/build/project-structure#the-agents-document) from these files alone, with nothing to install and no code that runs in your process.

An agent that uses in-process tools runs only from the process that defines it, and isn't published. One that builds its document with other npm packages can be published from code with `project.agents.publish({ agent })`, which publishes the module written from its document.

## Try a draft

A draft changes nothing anyone uses, so try it before publishing. `test_agent` starts one test session of the draft, the same test **Build** runs, with the first message you or the agent give it. It runs as you, with what the draft requires, so it asks you first. `read_agent_test` reads the session's state and the draft's latest reply.

If the draft still needs something chosen, such as a model or a sign-in, nothing starts; try it once from **Build** to choose.

## Drafts and publishing

Each change makes a new numbered draft. A draft changes nothing anyone uses: chats, channel installs, and anyone fetching the agent by name keep using its published version. `check_agent` runs every check publishing runs, storing nothing.

Publishing is the checkpoint. `publish_agent` publishes one draft as the agent's next version, and Final keeps that draft's files with it, so every published version can be opened, compared, and rolled back to. See [publishing](/operate/publishing).

Any agent published with its source can be changed on Final, wherever it was published from: its first change starts draft 1 from the published source. When the agent is published again from its repository with `final-agents publish`, that version becomes the next draft, and changes you hadn't published yet are merged onto it. A version that lacks changes published on Final since that repository last published is refused with `draft_conflict`, and the draft it names merges the two, so a publish never undoes work published on Final.

The tools are a client of [the drafts API](#the-drafts-api), which you can call yourself.

## Copy an agent and keep it current

`create_agent` can start from a published agent, including a public one such as `acme/release-assistant`. The copy is yours to change, and it remembers the agent it came from.

When the original publishes a new version, `update_agent_from_upstream` merges it into your copy as a new draft, file by file, keeping your changes. Where both changed the same lines, the file keeps both sides between standard conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`), and the result names the files. Resolve them with `edit_agent_file`, run `check_agent`, and publish.

## The drafts API

Build, the agent tools, and your own code use the same API, through `@finalai/agents/client`:

```ts
const { agent, draft } = await project.agents.create({ name: 'release-assistant', source });

const next = await project.agents.drafts.create({
  agentId: agent.id,
  base: draft.number,
  files: { 'instructions.md': 'Ship only when CI is green.\n' },
});

const checked = await project.agents.drafts.check({ agentId: agent.id, draft: next.number });
if (checked.diagnostics.length === 0)
  await project.agents.drafts.publish({ agentId: agent.id, draft: next.number });
```

| Method | What it does |
| --- | --- |
| `project.agents.create({ name, source })` | Creates an agent from its source and publishes its first draft. `{ name, from: { agentId } }` makes a copy that tracks the original. |
| `drafts.list({ agentId })` | The agent's drafts, newest first, whether you can change them, and the agent it tracks. |
| `drafts.get({ agentId, draft })` | One draft with its files (`'latest'` for the newest). |
| `drafts.create({ agentId, base, files })` | The next draft: `files` sets a path's text, or removes it with `null`. `base` is the newest draft, or `null` for an agent without drafts. Fails with `draft_conflict` when another draft landed first. |
| `drafts.check({ agentId, draft })` | The problems publishing would find, or the document it would make. Stores nothing. |
| `drafts.publish({ agentId, draft })` | Publishes a draft under the agent's name. Fails with `agent_source_invalid` when its checks do. |
| `drafts.mergeUpstream({ agentId })` | Merges the tracked agent's newest version into a new draft. |

`client.agents.drafts` is the same API, by agent ID from any client.

## Learn from the docs

Every agent in Final has two docs tools, so it learns the SDK from these pages instead of from a long prompt:

| Tool | What it does |
| --- | --- |
| `search_docs` | Finds the final.ai/docs pages that match a query, with a snippet from each. |
| `read_doc` | Reads one page as Markdown, by its path. |

An agent building an agent reads this page first, then looks up what it needs, such as [tools](/build/tools), [requirements](/build/requirements), or [integrations](/build/integrations), as it goes.

## Ask for the least the work needs

Final runs agents from source alone, so tools and hooks are [serverless](/build/tools#in-process-or-serverless). Beyond that, request the least the work needs: the lowest [permission ceiling](/build/requirements#harness), the fewest sandbox capabilities, and integrations narrowed to the tools the agent uses. Prefer an integration the person already has over writing a tool. An agent that works on Tasks keeps Final's Task tools; see [Final's gateway](/build/integrations#finals-gateway).
