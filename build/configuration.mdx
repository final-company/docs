`defineAgent` takes one object that is everything the agent is. It names nothing that runs the agent (no harness, model, machine, server, or credential); those come from whoever starts it, through [requirements](/build/requirements).

```ts agent.ts
import { defineAgent, files, markdown } from '@finalai/agents';

export const agent = defineAgent({
  name: 'Release Assistant',
  description: 'Checks whether a release is ready to ship.',
  instructions: markdown('./instructions.md', { from: import.meta.url }),
  workspace: files('./workspace', { from: import.meta.url }),
  secrets: ['RELEASE_SERVICE_TOKEN'],
  toolPolicy: { 'files.write': 'ask' },
  require: {
    harness: { permissionMode: 'review' },
    compute: { files: 'write', shell: 'execute' },
  },
});
```

## Identity

<ParamField path="name" type="string" required>
  The display name people see in Final. It's not the name you publish under; you choose that when you [publish](/operate/publishing).
</ParamField>

<ParamField path="description" type="string">
  One sentence on what the agent does.
</ParamField>

<ParamField path="avatar" type="AgentAvatarIface">
  An image or animation shown for the agent in Final's apps.
</ParamField>

## What the agent knows

<ParamField path="instructions" type="string | markdown(...) | array" required>
  System instructions for the harness. Several are joined by a blank line. See [instructions and skills](/build/instructions-and-skills).
</ParamField>

<ParamField path="skills" type="skill(...)[]">
  Procedures the agent loads when a task needs one.
</ParamField>

<ParamField path="workspace" type="files(...) | Record<string, string>">
  Files written once into the workspace of whatever sandbox provides `files`, such as config files the agent should start with. Paths are relative to the workspace.
</ParamField>

## What the agent can do

<ParamField path="tools" type="Record<string, tool>">
  The agent's own tools, made with `defineServerlessTool` or `defineInProcessTool`. The key is the tool's name. See [tools](/build/tools).
</ParamField>

<ParamField path="hooks" type="Record<string, hook>">
  Code that runs on session events, made with `defineServerlessHook` or `defineInProcessHook`. The key is the hook's name. See [hooks](/build/hooks).
</ParamField>

<ParamField path="secrets" type="string[]">
  Project secrets the agent's own code may read with `ctx.secrets.get(name)`. Reading a secret that isn't listed fails. See [secrets](/operate/authentication#use-secrets-in-your-code).
</ParamField>

What starts work isn't part of the definition either: [schedules](/build/schedules) are timers in a conversation, and [channels](/build/channels) are installed in a project.

## What the agent requires

<ParamField path="require" type="object" required>
  `harness` (required), `compute`, and `integrations`. See [requirements and providing](/build/requirements).
</ParamField>

## Approvals for the harness's own tools

<ParamField path="toolPolicy" type="Record<string, 'allow' | 'ask'>">
  Asks before, or allows, the harness's built-in tools by capability or name, such as `shell` or `files.write`. It applies within the permission mode the harness runs with, so `toolPolicy: { 'files.write': 'ask' }` keeps asking before edits even when the caller allows more. The harness must support native tool policies; mark `nativeToolPolicy` as an optional feature if the agent can run without it.
</ParamField>

Approvals for your own tools are set on each tool, and for integration tools on the slot. See [ask before a tool runs](/build/tools#ask-before-a-tool-runs) and [integrations](/build/integrations#choose-which-tools-the-agent-gets).
