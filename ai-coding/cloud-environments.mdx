A cloud environment is a Final computer: a cloud machine with your repository checked out, your toolchain installed, and your app able to start. The agent runs commands there, so it can install packages, run tests, and open your app in a browser without touching your laptop.

The goal is a computer you never set up by hand twice. You get there in two steps: a setup script in your repository, and, for Final agents, a sandbox setup that runs it on every new computer.

## Create a computer

Go to **Developer** > **Computers**, enter a name, and click **Create computer**. Once it's **Running**, you can work in it from the dashboard:

| Action | What you get |
| --- | --- |
| **Open editor** | VS Code in your browser, with a terminal on the computer. |
| **Start desktop**, then **Open screen** | A Linux desktop with a browser, for checking UI changes. |
| **Files**, **Processes**, **Activity** tabs | The computer's files, running commands, and lifecycle history. |
| **Settings** tab | The computer's name, preview port, stop timer, and **Allow internet access**. |

New computers use the **Desktop (default)** image. If your stack needs heavy system dependencies, build a container image with them preinstalled, add it with **Import a container image**, and choose it under **Image for new computer**. See [images and templates](/vm-platform/images-and-templates) for more on images.

## Write a setup script

Put everything it takes to go from a fresh clone to passing tests in one script in your repository. It's the single source of truth for your environment: you run it on a computer you opened yourself, a sandbox setup runs it for Final agents, and new teammates can run it on their laptops.

```bash scripts/setup.sh
#!/usr/bin/env bash
# Prepare a fresh checkout for development. Safe to run more than once.
set -euo pipefail
cd "$(dirname "$0")/.."

# Dependencies, exactly as pinned in the lockfile.
npm ci

# Local config with development-only values.
[ -f .env.local ] || cp .env.example .env.local

# Development database with schema and test data.
npm run db:migrate
npm run db:seed
```

Keep it idempotent, so running it twice does no harm, and keep secrets out of it: copy development defaults from a committed `.env.example`, and have people supply real credentials themselves. Make it executable and commit it:

```bash
chmod +x scripts/setup.sh
git add scripts/setup.sh && git commit -m "Add setup script"
```

When you work on a computer yourself, run `./scripts/setup.sh` after you clone, then run the tests to confirm the computer is ready. When a task turns up a missing dependency, fix the script, not the computer, so the next computer gets the fix too.

## Prepare computers for a Final agent

A Final agent gets its computer from whoever starts it, so the computer needs a recipe. That recipe has two parts with separate jobs:

| Part | What it holds | Where it lives |
| --- | --- | --- |
| **The computer's environment** | The base image, toolchains baked into it ahead of time, machine size, region, and idle timeout | The `computer({ image, build, ... })` options |
| **A sandbox setup** | The repositories to check out, environment variables, setup steps, services to start, named commands, network rules, and notes for the agent | A [sandbox setup](/build/sandbox-setups), which works on any provider |

Final builds the slow part, the `build` steps, into a base ahead of time. When a computer is created from it, Final checks out your repositories, runs your setup steps once, and starts your services before the agent's first command.

### Describe the environment

```ts storefront.ts
import { computer, defineSandboxSetup } from '@finalai/agents/sandboxes';

// Baked into the base once: system tools, not your code.
export const environment = computer({
  image: 'docker.io/library/node:26-bookworm',
  build: {
    steps: [{ run: 'apt-get update && apt-get install -y --no-install-recommends sqlite3' }],
    verify: [{ run: 'node --version && sqlite3 --version' }],
  },
});

// Applied to every new computer.
export const setup = defineSandboxSetup({
  repositories: [{ alias: 'storefront', repository: 'acme/storefront', ref: 'main' }],
  steps: [{ cwd: 'storefront', run: './scripts/setup.sh' }],
  services: [{ name: 'web', cwd: 'storefront', run: 'npm run dev -- --port 3000', port: 3000 }],
  commands: {
    e2e: { cwd: 'storefront', run: 'npm run test:e2e', description: 'Run the browser tests against the dev server.' },
  },
  notes: 'The dev server listens on port 3000.',
});
```

Paths are relative to the computer's working directory, so `cwd: 'storefront'` runs in the checkout. `box.description()` and the sandbox description file inside the computer list the real paths.

### Publish the setup for your team

Publish the setup by name so everyone who starts the agent uses the same version:

```ts publish-setup.ts
import { createClient } from '@finalai/agents/client';
import { setup } from './storefront.js';

const client = createClient({ auth: { apiKey: process.env.FINAL_API_KEY! } });
const project = client.project({ id: process.env.FINAL_PROJECT_ID! });

const published = await project.sandboxSetups.publish({ name: 'storefront', setup });
console.log(`storefront version ${published.version}`);
```

Each publish creates a new version that never changes. In the dashboard, published setups are listed under the project's **Sandbox setups** settings, and the project's **Sandbox for new chats** setting chooses the provider, its options, and the setup Final uses when it starts the project's agents in chats.

### Start an agent on it

When you start a coding agent yourself, create the computer from the environment and setup, and provide it for the agent's files and shell:

```ts start.ts
import { createClient } from '@finalai/agents/client';
import { finalCredits, serverlessNanocodeClaude, subscription } from '@finalai/agents/harnesses';
import { environment } from './storefront.js';

const client = createClient({ auth: { apiKey: process.env.FINAL_API_KEY! }, localCompute: false });
const project = client.project({ id: process.env.FINAL_PROJECT_ID! });

const agent = await project.agents.get({ name: 'storefront-coder' });
const setupId = (await project.sandboxSetups.list()).find((s) => s.name === 'storefront')?.id;
if (setupId == null) throw new Error('Publish the storefront setup first');

const sessionId = crypto.randomUUID();
const box = await project.sandboxes.create(environment, {
  setup: { setup: setupId, version: 'latest' },
  ownedBy: { session: sessionId },
});

const { response } = await project.sessions.create({
  id: sessionId,
  agent,
  provide: {
    harness: serverlessNanocodeClaude({
      model: 'claude-opus-5-5',
      inference: [subscription(), finalCredits()],
    }),
    compute: { files: box, shell: box },
  },
  message: 'Run the test suite and tell me how many tests pass.',
});
console.log(await response!.text());
```

The computer belongs to the session and is deleted with it. For parallel tasks, give each task its own session and computer, so each gets its own checkout and database.

<AccordionGroup>
  <Accordion title="Setup reference">
    | Part | Runs | Notes |
    | --- | --- | --- |
    | `build.steps` (computer) | Once per base build | Toolchains and system packages. Each step has `timeoutMinutes` (default 20). |
    | `build.verify` (computer) | After `build.steps` | Checks that fail the build if they fail. |
    | `steps` (setup) | Once per new computer | Runs after repositories are checked out. A failing step stops the computer from being used unless it's `optional`. Default timeout twenty minutes; set `timeoutSeconds` to change it. |
    | `services` (setup) | Every computer start | Long-running processes. A `port` appears in the sandbox description with its URL. |
    | `commands` (setup) | When the agent runs them | Named scripts, listed to the agent with their `description`. |

    See [sandbox setups](/build/sandbox-setups) for every field.
  </Accordion>
</AccordionGroup>

## Preview your app

The fastest way to check a UI change is the computer's own browser: click **Start desktop**, then **Open screen**, and open `http://localhost:3000`.

To share a preview with someone else, open the computer's **Settings** tab, enter the port under **Preview port**, and click **Publish port**. A public port is reachable by anyone with its URL, so use it only with development data. To keep the port private, create a short-lived token for it on the **Tokens** tab instead. See [networking](/vm-platform/networking) for custom domains and access rules.

## Troubleshooting

<AccordionGroup>
  <Accordion title="The computer's base build failed">
    A `build.steps` or `build.verify` command exited with an error. Run the same commands on a computer created from the same image to see the output, fix the step, and try again. Final retries temporary failures on its own before it marks a build failed.
  </Accordion>
  <Accordion title="A setup step fails because a checkout is missing">
    A step uses a repository alias as `cwd`, but no repository with that alias was checked out. Check that the alias in `repositories` matches the `cwd` exactly, and that the project can reach the repository.
  </Accordion>
  <Accordion title="A setup step fails">
    The computer isn't used until required steps succeed. Run the step by hand on the computer to see its output, fix your setup script, and try again; steps that already finished aren't run again.
  </Accordion>
  <Accordion title="Package installs fail with network errors">
    Open the computer's **Settings** tab and check **Allow internet access**. Network allowlists and denylists still apply, so also check that your package registry is allowed.
  </Accordion>
</AccordionGroup>
