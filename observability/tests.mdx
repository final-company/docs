A test suite is a set of cases your agent should get right, checked by judges. Runs score a candidate, such as a commit, and compare it with a baseline to find regressions.

## Suites and versions

A suite has a name, description, labels, numbered published versions and one draft. Edit the draft, then publish it as the next immutable version, or discard it. Runs always use a published version.

```ts
const suite = await project.tests.createTestSuite({ name: 'Refunds', labels: ['support'] });
// add cases to the draft, then:
await project.tests.publishTestSuite({ testSuiteId: suite.testSuiteId, notes: 'Initial cases' });
```

## Cases and checks

A case has a name, an input, checks, tags, metadata and optionally a trace. Its `caseId` stays the same across suite versions, so results compare case by case.

A check compares one judge's output with an expected value. It pins the judge's major and minor version, so a rubric change can't silently change what a check means. Operators are `eq`, `ne`, `lt`, `lte`, `gt`, `gte`, `in` and `not_in`. Judges never see `expected` or `rationale`.

```ts
import { TestCheckOperator } from '@finalai/observability/contract';

await project.tests.addTestCases({
  testSuiteId: suite.testSuiteId,
  cases: [
    {
      name: 'Duplicate charge',
      input: { question: 'I was charged twice for order 1042' },
      checks: [
        {
          judgeId: groundedJudgeId,
          judgeMajor: 2,
          judgeMinor: 0,
          op: TestCheckOperator.Eq,
          expected: 'Grounded',
          rationale: 'The order lookup shows both charges.',
        },
      ],
      tags: ['billing'],
    },
  ],
});
```

| Operation | What it does |
| --- | --- |
| `add_test_cases` | Adds up to 1,000 cases to the draft. |
| `add_test_cases_from_traces` | Adds cases from traces: their input, the trace link and the checks you give. |
| `add_test_cases_from_dataset` | Adds cases from a dataset version, mapping a column to the input. |
| `update_test_case`, `remove_test_case` | Change or remove a case in the draft. |
| `repin_test_suite_checks` | Moves the draft's checks for a judge to another version. |

To turn production failures into cases, ask the [observability agent](/observability/agent) or call `add_test_cases_from_traces` with the failing traces.

## Run modes

| Mode | What runs | Use it for |
| --- | --- | --- |
| `external` | Your own runner executes each case and links its trace with `testCase`. | Agents that run outside Final, in CI or locally. |
| `stored_traces` | Nothing executes; each case's linked trace is scored again. | Checking a new judge version, or rescoring evidence you already have. |
| `native` | Final runs a Final agent or workflow revision per case, with a concurrency limit. | Agents and workflows built on Final. |

Start a run with `start_test_suite_run` or [`final-obs test run`](/observability/tests-in-ci). Options: `version`, `mode`, `caseSelection` (`all`, `tags`, `case_ids` or `last_failures`), `repeats` (1 to 20), a `candidate` label such as a commit SHA with `candidateMeta`, `nativeCandidate` for native runs, and `trigger`.

### External runs

Your runner gets a run ID and executes each case inside `testCase`. The case runs as the root of a new trace carrying `final.test.run_id` and `final.test.case_id`, and the link travels as baggage to every service the case calls through `inject`.

```ts
import { init, shutdown, testCase } from '@finalai/observability/node';

init({ environment: 'test' });

for (const { caseId, input } of cases) {
  await testCase({ runId: process.env.FINAL_TEST_RUN_ID!, caseId }, () => agent(input));
}
await shutdown();
```

Pass `repeat` (0-based) when a run repeats cases. Only the first trace per case and repeat is scored. Use the `test` environment so online judges and monitors ignore test traffic.

### Native runs

```ts
import { NativeCandidateKind, TestRunMode } from '@finalai/observability/contract';

await project.tests.startTestSuiteRun({
  testSuiteId: suite.testSuiteId,
  version: 3,
  mode: TestRunMode.Native,
  nativeCandidate: { kind: NativeCandidateKind.Agent, id: agentId, revision: 'rev_2', concurrency: 5 },
});
```

Each case runs through the public agents or workflows API with the case's input, and the trace context propagates into the run.

## Results

A run moves through `pending`, `running` and `scoring` to `completed`, `failed` or `cancelled`. `get_test_suite_run` counts cases in total, with output, scored and passed. `get_test_suite_run_results` returns each case's outcome (`passed`, `failed`, `errored`, `no_output` or `pending`), trace, checks, judge output, reason and error. `cancel_test_suite_run` stops a run.

Executing again and rescoring are separate: `score_test_suite_run` creates a new run that scores a run's stored evidence against the latest checks, without executing anything.

## Comparison

`compare_test_suite_runs` pairs cases between a baseline run and a candidate run:

| Change | Meaning |
| --- | --- |
| `regressed` | Passed in the baseline, fails now. |
| `fixed` | Failed in the baseline, passes now. |
| `still_passing`, `still_failing` | Unchanged. |
| `flaky` | Passes in some repeats and fails in others. |
| `added`, `removed` | In only one of the runs. |

It also reports the number of regressions, fixes and flaky cases, and the cost and latency deltas.
